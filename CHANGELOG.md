# Changelog

## 0.2.0

- Changed: requires Node.js 22.12 or later. Node.js 18 and 20 are end-of-life, and the test tooling no longer runs on them.
- Changed: the SDK no longer scrubs kept values for emails and card numbers. Earlier releases replaced email addresses and 16-digit numbers inside kept strings with `<masked>` until the project had any global rule, so some projects had this and others did not. Masking is now decided only by your own rules: a field without a `keep` rule is masked as before, and a kept field is sent as it is, even when it holds an email address or a card number. What to check: look at the fields you keep. If a kept field can hold an email address, a card number or other personal data, remove the `keep` rule, or add a field mask or regex mask for it in the project's global rules.
- Changed: a synced regex mask whose pattern Python also rejects now masks every kept string, with one warning naming its index, instead of being skipped. This matches patterns that have no JS translation, which already did so, and the Python SDK. A malformed entry in the project's global rules (for example a pattern that is not a string) used to make the SDK ignore all of them, field masks included; now the valid rules still apply and every kept string is masked. Fix or remove the entry to get kept values back.
- Fixed: a request or response body labelled `application/x-www-form-urlencoded` that is not `key=value` pairs, such as free text, was sent with the whole text as a field name. A form body in which any `&`-separated part has no `=` is now masked as a whole, and no field names or value types are taken from it.
- Fixed: the capture's `domain` is now only the host and port, also when the pipeline is called directly with a URL that holds `user:password@`. The http hook already stripped it. Replay now also ignores userinfo when matching a request to a recorded endpoint. A bundle whose domain holds `user:password@` from an earlier capture no longer matches; record and pull it again.
- Changed: `User-Agent`, `Cache-Control` and `Accept-Language` values are masked by default. All three can carry data about your users or your customers, so they are no longer on the header allowlist. In requests and responses their values are sent as `<masked>` unless you keep them: a `header.user-agent`, `header.cache-control` or `header.accept-language` keep rule for the request, `resp_header.user-agent`, `resp_header.cache-control` or `resp_header.accept-language` for the response. The names are still sent. Replayed responses carry `Cache-Control: <masked>` unless you keep `resp_header.cache-control`. The six values still sent as they are: `content-type`, `content-length`, `accept`, `accept-encoding`, `host` and `transfer-encoding`.
- Removed: the `EMBEDDED_REGEX_MASKS` export. `MAX_BACKSTOP_SCAN_CHARS` is renamed `MAX_REGEX_SCAN_CHARS`, and `CompiledRules.untranslatable` is renamed `CompiledRules.unusable`.
- Fixed: a case-insensitive regex mask (`(?i)` or the rule flag `i`) now matches `İ` (U+0130) and `ı` (U+0131) wherever it matches `i`, and the other way round, as the Python SDK does. Before, Node left them unmasked where Python masked them. One case-folding difference remains: under `i`, the combining mark U+0345 counts as a word character for `\w`, `\W`, `\b` and `\B`, where Python does not count it; this only affects text with U+0345 next to a letter or digit.
- Added: turning off automatic ID grouping in paths. The SDK turns path segments that look like IDs (all digits, a UUID, or 16 or more hex characters) into `{id}`. A project can now turn that off with the dashboard setting "Group IDs in paths automatically". When it is off, only the project's path patterns group paths, and every other segment is sent as written. The SDK reads the setting from `project_settings` in the rules sync, and replay reads it from the bundle, so replay groups paths the way capture did. Until a sync says otherwise the setting is on, which is the behaviour of earlier releases.
- Changed: the value-type labels and the rules for ID segments are generated from a shared spec, `tools/classifiers/classifiers.json`, the same spec the Python SDK uses. Captures now carry `classifier_spec_version`, so the server can tell which version of the labels a capture used. The labels and rules themselves are unchanged.
- Fixed: a capture processed before the first rules sync was sent with IDs grouped even on a project that turned "Group IDs in paths automatically" off, so one endpoint could arrive as `/orders/{id}` and then as `/orders/123`. The sender now holds such a capture, for at most 5 seconds from client start, until the first sync arrives, then applies the project's setting. If no sync arrives in that time it is sent as before, and a flush (`flush()`, `close()` or the exit hook) sends held captures at once. The capturing call is never delayed.
- Changed: the warning for a 404 from `GET /v1/sdk/sync` now says what still applies. Before any successful sync it says every captured value is masked; after one, it says the rules from the last successful sync stay in effect and anything they do not cover is masked in full. A successful sync resets the warning, so each outage logs it once, where before it was logged once per client. Masking is unchanged.

## 0.1.1

- Fixed: a 404 from `GET /v1/sdk/sync` (for example a wrong `backendUrl`) no longer switches the SDK to the legacy anonymizer rules, which left request and response bodies and query values mostly unmasked. Legacy mode is removed. A 404 now keeps any rules already synced, leaves the first sync unmarked so captures stay fully masked and novel, and logs one warning per client that names the sync URL and the backend URL.
- Fixed: `field_masks` from the project defaults were ignored once rules had synced, so a field that a rule kept (such as `password`) was sent in cleartext. A name in `field_masks` is now masked even when kept: JSON keys mask their whole subtree, and form fields, query parameters and request and response headers are masked by name, compared case-insensitively.
