# Test parity with the Python SDK

This file maps every masking, path, fail-closed and size-limit behaviour that the Python SDK tests to the Node
test that covers the same behaviour. The reference is the Python SDK at release 0.8.0. That is the version
recorded in `conformance/VECTORS_VERSION`.

## Keeping this file current

- Any release of the Python SDK that adds, removes or changes a masking, path, fail-closed or size-limit test
  updates this file in the same release. That includes changes to the shared vector files.
- Any Node change that adds or renames a test listed here updates the matching row.
- When a row moves from PARTIAL to MATCH, the Node test must use the Python test's inputs and expected
  outputs. Do not change the Python side to make the row match.
- Status meanings:
  - **MATCH**: the Node test uses the same inputs and asserts the same expected outputs. Extra Node
    assertions are allowed. **MATCH (shared vector)** means the Node test is a case of a vector file that both
    SDKs run, so the inputs are byte-identical and the expected outputs were produced by the Python SDK. The cell
    names the file and the cases, and the Node unit test that was there before stays and is named too. A case
    name ending in `/*` stands for every case of the file whose name starts with the text before it; the
    bracketed number is how many that is.
  - **PARTIAL (inputs only)**: the Node test asserts the same behaviour and expects the same outcome, but runs
    different literal inputs, or reaches the same behaviour through a different trigger. The cell says what
    differs.
  - **PARTIAL (behaviour differs)**: the Node output differs from Python's for the same call. The cell says how.
  - **N/A**: Node has no such concept, so there is nothing to test. The cell says why.
  - **Accepted difference**: an agreed difference between the SDKs that is not a defect. The cell says why.
- Node titles are cited as `file > describe > test title`. A title with a placeholder such as `%s` or `%j` is the
  `it.each` template, and the row names the case in brackets (`[case: ...]`) when it covers one case of several.
  Vector tests are titled by the vector name: `%s` is the case name in the vector file.

Python test ids are `file::Class::test`, relative to the Python SDK repository. Node test ids are
`file > describe > test title`. Rows for parametrised Python tests cover every case unless the row names a case.

## Shared vector files

`tests/vectors/field-rules-vectors.json` (Python) and `conformance/vectors/field-rules-vectors.json` (Node) are
byte-identical. Both have SHA-256 `1f63702dc03bf8f04ac44b8186257c61a150a0e6d73f1ef8fa226e8134cc5e70`. Each runner
iterates all 36 vectors, so each produces 36 test results. Both run with no placeholder salt. The other files in
`conformance/vectors/`, apart from the four listed below, are generated from the Python SDK by
`tools/gen-vectors.py`. They use their own inputs, not the inputs of the Python unit tests, so they count as
MATCH only where a row says the inputs agree.

| Behaviour | Python test | Node test | Status |
| --- | --- | --- | --- |
| All 36 shared field-rule vectors: request and response bodies, headers, query, keep and mask rules, status scopes | tests/test_field_rules_vectors.py::test_field_rules_vector (36 cases) | test/privacy/field-rules-vectors.vectors.test.ts > field-rules-vectors (shared with the browser masker) > %s [one case per vector name, 36 cases] | MATCH |

Four more files are authored in the Python repository under `tests/vectors/` by `tools/gen_shared_vectors.py`
and copied here byte for byte into `conformance/vectors/`. Their cases are `{name, op, input, expected}`: `op`
picks one of a few operations that each runner implements, and the `description` of each file defines the
operations it uses. Every expected value is produced by calling the Python SDK. Each Masking and Fail-closed row
(and the regex scan cap rows of Size limits) that can be written as data cites a case of these files, and
`test/privacy/shared-vectors.vectors.test.ts` runs every case. The rows that cannot be written as data stay
as they are, and each file's description lists them with the reason.

  `TestPipelineFingerprintValueDiscrimination` in `tests/test_pipeline.py`. Only the tests named in a row above are
  listed, for example `TestExtractKeypaths::test_values_excluded`, which asserts that values never appear in key paths.

  `TestSendCompression`.
- What the hooks record rather than what is masked, in `tests/test_capture.py`: request content-type inference and the
  query-parameter fingerprint of a `requests` call.
